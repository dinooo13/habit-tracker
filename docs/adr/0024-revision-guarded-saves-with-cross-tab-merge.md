# 24. Revision-guarded saves with deterministic cross-tab merge

- **Status:** Accepted
- **Date:** 2026-08-31

## Context

Every tab holds the full Pinia state and the bootstrap watcher debounce-saves whole snapshots
through `DexiePersistenceAdapter.save()`, which `clear()`s and `bulkPut()`s each collection. Two tabs
open on the same IndexedDB database are therefore last-writer-wins: edit in tab A, touch anything in a
stale tab B, and B's debounced save silently reverts A's edits. This is the most realistic data-loss
scenario for a local-first, backend-less app (ADR-0002, ADR-0003), and ADR-0017 explicitly recorded
cross-tab save coordination as out of scope at the time.

## Decision

Give the persisted envelope a **revision**, guard every write against it inside the Dexie
transaction, keep idle tabs fresh over a `BroadcastChannel`, deterministically three-way-merge
non-overlapping edits, and prompt only when two tabs changed the *same* record incompatibly.

- **Revision as storage metadata.** A monotonic `revision: number` lives in the existing `meta` table
  (a third row beside `schemaVersion` and `settings`), **not** in `AppDataV2`. `APP_DATA_SCHEMA_VERSION`
  stays `2`; the Zod schemas, migrations, exports and imports are byte-compatible; no Dexie
  store-version bump is needed. Absent ⇒ `0` for every existing install, so there is no migration step.
  A backup file never carries a revision (it is device-local).
- **Compare-and-swap write barrier (extends ADR-0009).** `save(payload, expectedRevision)` performs a
  read-compare-write inside the existing `rw` transaction over `habits, entries, suggestions, meta`;
  IndexedDB serialises transactions across tabs, so this is atomic with no extra locking. When
  `expectedRevision` is a number and the stored revision has moved on, the transaction aborts with a
  `StaleWriteError` carrying **only** the revisions (validating a whole envelope under a write lock is
  avoided; the caller re-loads for the merge anyway). `expectedRevision === null` **force-writes** —
  the path for authoritative, user-initiated whole-envelope replacements (import, delete-all, demo,
  legacy migration), which should win over a peer tab's incidental edit. The adapter also exposes a
  cheap `readRevision()` freshness probe.
- **Proactive refresh — `useCrossTabSync()`.** A `createCrossTabSync(deps)` factory plus a
  module-singleton accessor (the `use-reminder-engine.ts` pattern, issue #71) owns each tab's
  `knownRevision`, its last-observed stored `base` snapshot (the merge base), and the reactive
  `conflict` state. After every successful write it posts `{ saved, revision, tabId }` on
  `BroadcastChannel('habit-tracker:persistence')`; a clean, idle tab re-hydrates silently on a peer
  ping, on `visibilitychange → visible` / `focus`, and on a 30s visible-only poll (the fallback for
  browsers without the channel). Each trigger runs a cheap `readRevision()` probe first and only does a
  full `load()` when the revision actually moved. A **dirty** tab never re-hydrates — it lets its
  pending save hit the guard and merge, so in-flight edits are never discarded. `applyRemote()` cancels
  the echoed debounced save on `nextTick` to break the apply→save→broadcast loop.
- **Deterministic three-way merge (no CRDT).** On a `StaleWriteError` the saver re-loads and runs the
  pure `mergeAppData(base, ours, theirs)`. Records are keyed **habits by `id`**, **entries by
  `habitId:date`** (not `id` — `createId('entry')` is random, so two tabs backfilling the same
  habit-day produce logically-identical records with different ids), **suggestions grouped by
  `entryId`**, **settings per field**. For habits and entries, per key: if only one side differs from
  `base`, that side wins; if neither differs, keep `base`; if both changed to the same value, keep it;
  if both changed differently, or one deleted while the other modified, it is a **conflict**. When both
  sides *added* the same key that `base` lacked, they merge if the records are equal ignoring `id`
  (keeping the stored side's `id`) — the common auto-backfill case — and conflict otherwise.
  Suggestions are deterministic derived state (ADR-0005) so they **never** conflict: a group present on
  both sides takes the stored side, a group present on one side is kept, and any group whose `entryId`
  is absent from the merged entries is dropped (and regenerated by `reconcileDerivedState()` after the
  merge is applied). Settings **never** conflict: each field takes whichever side changed it, preferring
  *ours* when both changed, except `lastExportedAt` and `backupNudgeSnoozedUntil`, which take the later
  value. Everything not covered by that paragraph falls through to abort-and-prompt. Equality is
  explicit per type (`scheduleWeekdays` and `pauses` compared element-wise), not a generic deep-equal,
  so a field added to `Habit` or `HabitEntry` later forces a deliberate decision here. The re-merge loop
  is bounded (3 attempts) so a livelock degrades to the conflict prompt rather than spinning.
- **Prompt only on a real collision.** A conflict is surfaced through `useCrossTabSync().conflict`, a
  new reactive state kept **off** `useStorageHealth` — ADR-0017 fixed the persistence lifecycle at
  exactly four states (`ok | saving | failed | unavailable`), and ADR-0019 already set the precedent of
  a separate concern (quarantine) sharing the same UI surface. While a conflict is active the bootstrap
  watcher **suspends the debounced auto-save** (so nothing this tab does can clobber the other tab's
  data) and `PersistenceStatusIndicator.vue` renders a third `UAlert` offering **Export this tab's
  data** and **Reload with latest**. The newer stored data is never silently discarded — it is offered
  as an export first. `createPersistenceSaver` gains an `isConflictError` / `onConflict` short-circuit
  (mirroring its quota short-circuit) so a conflict never drives the retry/backoff loop or the
  `unavailable` banner. A silent background refresh shows the existing quiet pill ("Updated from another
  tab"), never a toast.

## Consequences

- **Pros:** the last-writer-wins clobber is closed by a transactional guard; non-overlapping edits merge
  silently with no user interruption; a genuine same-record collision prompts plainly and never loses
  the newer data. No new dependency, no schema bump, no migration — one extra `meta` row.
- **Trade-offs:** merging is deliberately limited to the non-overlapping case (KISS). Field-level merge
  inside a single habit/entry, operation logs, CRDTs, and an interactive per-record resolution UI are
  out of scope; anything past the one-paragraph rule set falls through to abort-and-prompt, losing at
  most the stale tab's unsaved delta and making that explicit. The teardown (`pagehide`) flush uses the
  guarded path with no retries: if the page dies mid-merge nothing is written, which is strictly better
  than today's clobber.
- **Supersedes nothing.** **Extends** ADR-0009 (adapter contract) and ADR-0017 (persistence lifecycle,
  whose "cross-tab out of scope" note this closes). The snapshot/debounce strategy (ADR-0004), the
  schema (ADR-0006, ADR-0010), the coaching engine (ADR-0005), and the day clock (ADR-0018) are
  unchanged.
